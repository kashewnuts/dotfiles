# PR レビュー（日本語）

GitHub Pull Request をレビューし、日本語で構造化された要約を出力する。

## 入力

`$ARGUMENTS` には以下のいずれかを指定:
- PR URL (例: `https://github.com/owner/repo/pull/123`)
- カレントリポジトリの PR 番号 (例: `123`)

## 処理手順

1. **PR 情報の取得**
   - `gh pr view $ARGUMENTS --json number,title,body,author,state,additions,deletions,changedFiles,labels,reviewDecision`
   - PR のメタ情報を取得

2. **変更内容の取得**
   - `gh pr diff $ARGUMENTS`
   - 変更されたファイルと差分を取得

3. **原則との照合**と 4. **機械チェック**
   - `~/.claude/skills/local-review-checks/SKILL.md` があれば、その「共通」の節と作業中のリポジトリの節を手順 3 と 4 として当てる。無ければ、手順 3 は自分の過去のレビュー指摘を基準に diff を見て、手順 4 はリポジトリの lint と CI の結果を見る
   - 結果は出力の「レビューポイント」と「機械チェック」の小節に書く

5. **変更の分析**
   - 変更の目的を推測
   - どのモジュールや機能に影響するか特定
   - 変更の種類を機能追加、バグ修正、リファクタリング、ドキュメントなどに分類

6. **レビューポイントの特定**
   - セキュリティ上の懸念
   - パフォーマンスへの影響
   - テストカバレッジ
   - コードスタイルの一貫性

7. **リスク評価**
   - 低: 小規模な変更、影響範囲が限定的
   - 中: 複数ファイルの変更、既存機能への影響あり
   - 高: 大規模な変更、破壊的変更の可能性

## 出力フォーマット

```markdown
## PR #XXX: [タイトル]

**作成者**: @username | **状態**: Open/Merged/Closed
**変更**: +X行 / -Y行 / Zファイル

---

### 概要

- **目的**: この PR が解決しようとしている問題や追加する機能
- **変更種別**: 機能追加 / バグ修正 / リファクタリング / ドキュメント
- **影響範囲**: 影響を受けるモジュールや機能

---

### 変更内容

| ファイル | 変更内容 |
|----------|----------|
| `path/to/file1.py` | 変更の説明 |
| `path/to/file2.py` | 変更の説明 |

---

### レビューポイント

- [ ] セキュリティ: 確認すべき点
- [ ] パフォーマンス: 確認すべき点
- [ ] テスト: 確認すべき点
- [ ] その他: 確認すべき点

#### 機械チェック

| 検査 | 結果 | 指摘文案 |
|------|------|----------|
| 検査の名前 | 警告の要約 | ラベル付きの文案 |

#### 指摘文案

MUST、SHOULD、IMO、NIT、ASK のいずれかのラベルで始め、公式ドキュメントかソース行か決定資料の URL を根拠として必ず添える。仕様や意図が分からないものは推定で直さず ASK にする。

#### 確認した根拠

- 公式ドキュメント・ソース行・Redmine note・Slack の URL と、そこで確かめた事実

#### 検討した代替案と採らなかった理由

- 既存のままを許容した判断 (スコープ外) も書く

#### 作者に確認したいこと (ASK)

- 実装の意図・合意事項との差・テストの期待値が変わった理由

---

### リスク評価

**リスクレベル**: 低 / 中 / 高

**理由**:
- リスク要因1
- リスク要因2

---

### 推奨アクション

1. アクション1
2. アクション2
```

## 注意事項

- PR の本文があれば、本文から目的を把握する
- コミットメッセージも参考にする
- 大規模な PR の場合は、主要な変更に焦点を当てる
- レビュー済みの場合は、既存のレビューコメントも考慮する
- リポジトリ固有の追加レビューは `local-review-checks` の節に置き、このファイルには書かない
